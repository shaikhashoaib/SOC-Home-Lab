# Ubuntu SSH Failed-Login Detection

**Project:** SOC Home Lab  
**Platform:** Splunk Enterprise on Windows + Splunk Universal Forwarder 10.4.3 on Ubuntu  
**Data source:** `/var/log/auth.log`  
**Index:** `main`  
**Status:** Controlled test and initial detection query completed

## 1. Objective

Forward Ubuntu authentication logs to the Windows-hosted Splunk Enterprise instance, generate a controlled failed SSH login, and practise extracting and counting failed-login activity.

## 2. Lab configuration and verification

- Ubuntu Server 24.04.5 LTS is running in the `SOC-Ubuntu` VirtualBox VM.
- Splunk Universal Forwarder 10.4.3 was installed on Ubuntu.
- The configured Splunk receiving endpoint is `192.168.56.1:9997`.
- The Windows Splunk receiver was confirmed listening on TCP port `9997`.
- Ubuntu-to-Windows TCP connectivity to `192.168.56.1:9997` was tested successfully.
- The forwarder was ultimately shown with `192.168.56.1:9997` under **Active forwards**.
- The `splunkfwd` service account was added to the `adm` group so it could read the Ubuntu authentication log.
- The monitor `/var/log/auth.log` was successfully added to the forwarder.
- Splunk search results confirmed Ubuntu events arriving with host `soc-ubuntu`, source `/var/log/auth.log`, sourcetype `auth`, and index `main`.

## 3. Verify incoming Ubuntu authentication events

```spl
index=main source="/var/log/auth.log"
```

A captured search returned **202 events** at the time of verification. This is a point-in-time count and will change as more log events arrive.

The event preview included SSH session activity and local `socadmin` activity from the Ubuntu VM.

## 4. Controlled failed SSH login test

A controlled test was run against the user's own Ubuntu lab by attempting an SSH login with the deliberately invalid username `wronguser` from Windows PowerShell. The attempt used the lab's forwarded SSH connection to the Ubuntu VM. Three failed-password records were visible in Splunk.

Search used:

```spl
index=main source="/var/log/auth.log" "Failed password"
```

Observed event details:

| Field | Observed value |
|---|---|
| Event count | 3 |
| Host | `soc-ubuntu` |
| Username | `wronguser` |
| Source IP | `10.0.2.2` |
| Service | SSH (`sshd`) |
| Message | `Failed password for invalid user` |

These are expected results from the controlled lab test. They are not evidence of an actual external attack.

## 5. Field extraction and threshold query

The following SPL extracts the username and source IP, groups the events, and returns groups with at least three failed attempts:

```spl
index=main source="/var/log/auth.log" "Failed password"
| rex "Failed password for (invalid user )?(?<username>\\S+) from (?<src_ip>\\d+\\.\\d+\\.\\d+\\.\\d+)"
| stats count as failed_attempts by username src_ip host
| where failed_attempts >= 3
| sort - failed_attempts
```

The extracted values were verified:

- `username`: `wronguser`
- `src_ip`: `10.0.2.2`

The threshold query was used as an investigation/search exercise. A scheduled Splunk alert has **not** yet been created.

## 6. Initial SOC assessment

The search identifies three failed SSH authentication attempts for the same invalid username from the same source IP in the selected search period. In a production environment, repeated SSH failures can warrant triage for password guessing or brute-force activity.

For this lab, the activity was intentionally generated by the analyst. A low severity / informational classification is appropriate for the test itself. Do not classify an event as malicious based only on a failed-login count; validate the source, time window, target account, surrounding activity, and whether the activity was authorised.

## 7. Suggested follow-up

- Create a scheduled alert using a clearly defined time window and threshold.
- Add a dashboard panel for failed SSH logins by source IP and username.
- Test a successful SSH login and compare it with failed-login records.
- Document triage steps, false-positive considerations, and response actions.
- Review and redact screenshots before adding evidence to the public repository.

## 8. Evidence and limitations

The results in this report are based on the lab screenshots and searches observed during the working session on 2026-11-07. Event counts and timestamps are snapshots, not permanent totals. The source IP is recorded exactly as Splunk displayed it; its broader network role has not been independently established here.

No passwords, tokens, or private keys are included in this report.
